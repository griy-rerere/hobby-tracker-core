# Архитектурный журнал решений — Hobby Tracker Core

**Дата:** 05–06.08.2026  
**Состояние:** Initial Architecture Baseline

## Цель проекта

Создать расширяемое ядро Hobby Tracker, которое не зависит от конкретного интерфейса (API, CLI, Telegram Bot) и инфраструктуры хранения данных.

Основной принцип:

> Сначала создаётся устойчивое ядро предметной области, затем вокруг него добавляются интерфейсы и инфраструктура.

---

# ADR-001 — Архитектура приложения

## Решение

Использовать разделение на слои:

```
domain
application
infrastructure
interfaces
```

## Обоснование

Ядро не должно знать:

- о базе данных;
- ORM;
- FastAPI;
- Telegram API;
- способе хранения данных.

Зависимости направлены внутрь:

```
Interface Layer
        ↓
Application Layer
        ↓
Domain Layer
```

---

# ADR-002 — Core как отдельный Python package

## Решение

`hobby-tracker-core` является отдельным пакетом.

Структура:

```
hobby-tracker-core/

src/
└── hobby_tracker/
    └── core/
        ...
```

## Обоснование

Ядро должно быть независимо используемым компонентом.

В будущем возможны:

- FastAPI приложение;
- CLI;
- Telegram Bot;
- другие клиенты.

# ADR-007 — Hobby как Entity

## Модель

```python
Hobby:
    id: UUID
    name: str
```

## Обоснование

Хобби обладает собственной идентичностью.

Два одинаковых по имени объекта могут быть разными сущностями.

---

# ADR-008 — ActivityEntry как Entity

## Модель

```python
ActivityEntry:
    id: UUID
    hobby_id: UUID
    started_at: datetime
    duration: timedelta
    note: str | None
```

## Обоснование

Активность имеет:

- собственный идентификатор;
- время начала;
- длительность;
- дополнительную информацию.

Она не является просто полем Hobby.

---

# ADR-009 — UUID вместо автоинкрементных ID

## Решение

Использовать UUID для идентификаторов сущностей.

## Обоснование

Преимущества:

- независимость от БД;
- удобная синхронизация;
- возможность создавать сущности до сохранения;
- отсутствие необходимости получать sequence из БД.

## Статус

Предпочтительный вариант:

```
UUID7
```

---

# ADR-010 — Генерация ID

## Решение

Не делать предварительную проверку существования UUID.

Не использовать:

```python
if not exists(id):
    save()
```

## Обоснование

Такая проверка:

- создаёт лишний запрос;
- не решает проблему гонок;
- всё равно требует ограничения БД.

Ответственность:

```
UUID Generator
        ↓
Repository
        ↓
Database Constraint
```

# ADR-011 — Repository Pattern

## Решение

# ADR-012 — Отказ от Generic Repository

## Решение

Не использовать:

```python
Repository[T]
```

## Обоснование

Разные сущности имеют разные операции.

Например:

Hobby:

```
find_by_name()
rename()
```

ActivityEntry:

```
find_between()
sum_duration()
```

Специализированные интерфейсы лучше отражают предметную область.

      ↓

# ADR-015 — Использование __call__ для Use Cases

## Решение

Use Case вызывается через:

```python
use_case(request)
```

## Обоснование

Use Case представляет действие пользователя.

Пример:

```python

```

# ADR-016 — Асинхронность

## Решение

Не делать весь код async заранее.

## Обоснование

Асинхронность нужна преимущественно для:

- базы данных;
- сетевых операций;
- внешних API.

Доменная модель от неё не зависит.

---

# ADR-017 — Request объекты для команд

## Решение

Использовать Request для операций изменения состояния.

Примеры:

```python
CreateHobbyRequest

AddActivityEntryRequest
```

## Обоснование

Позволяет расширять API без изменения сигнатур.

Вместо:

```python
create(name, color, group_id, ...)
```

используется:

```python
create(CreateHobbyRequest(...))
```

---

# ADR-018 — Простые Query без Request

## Решение

Для небольших запросов допускается передача параметров напрямую.

Пример:

```python
GetHobbyDuration(
    hobby_id,
    date_range
)
```

## Обоснование

Не создавать дополнительные классы без необходимости.

---

# ADR-019 — timedelta вместо int минут

## Решение

В доменной модели использовать:

```python
timedelta
```

а не:

```python
int
```

## Обоснование

Домен работает с понятием времени, а не количеством минут.

# ADR-020 — DateRange

## Решение

Использовать объект диапазона дат:

```python
DateRange:
    start: date
    end: date
```

## Статус

Value Object.

Допускается упрощение до отдельных параметров, если объект используется только в одном месте.

# ADR-021 — Минимальная статистика

## Решение

Не создавать универсальный объект:

```python
Statistics
```

на раннем этапе.

## Обоснование

Пока основная метрика:

```
duration
```

Более сложная статистика будет добавляться при появлении реальных требований.

---

# ADR-022 — Агрегация данных в базе

## Решение

Суммирование длительности выполняет БД.

Не:

```
SELECT *
↓
Python sum()
```

А:

```
SELECT SUM(duration)
```

## Обоснование

База данных лучше подходит для агрегирующих операций.

---

# ADR-023 — Repository может содержать операции агрегации

## Решение

Допустимы методы вида:

```python
sum_duration(
    hobby_id,
    date_range
)
```

## Обоснование

Репозиторий отвечает за эффективное получение данных.
